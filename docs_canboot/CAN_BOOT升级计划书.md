# 装甲板 CAN Bootloader 升级计划书

版本：v0.4（独立升级总线，1–4 块装甲板）
日期：2026-09-24
适用工程：`new_armor/Armor_Cmzy26_081`；升级主站为 PC + USB-CAN

## 1. 已冻结的用户决策

| 项目 | 决策 |
|---|---|
| 升级主站 | PC + USB-CAN 直接连接装甲板 CAN 总线 |
| Bootloader 首次安装 | 四块板先通过 SWD 烧录一次 |
| 最大应用槽位 | 48 KB（受 STM32L432KB 128 KB Flash 限制） |
| 升级期间 | 允许进入维护模式，暂停击打检测和普通业务通信 |
| 完整性保护 | CRC32；暂不做加密和数字签名 |
| 多板策略 | PC 顺序升级，一次只选一块板，按完整 UID 定址 |
| 升级接线 | 允许一台 PC 的 USB-CAN、L431 和 1–4 块装甲板同时在线；装甲板收到有效升级选择后暂停比赛 CAN 业务并进入 Bootloader |

## 2. 目标和不可破坏性要求

### 2.1 目标

通过 500 kbps 经典 CAN 给指定装甲板升级应用固件，PC 工具能够发现当前连接的 1–4 块板、选择目标、传输 `.bin`、显示进度、校验结果和回退结果。

### 2.2 必须满足的安全不变量

1. Bootloader 永远位于 Flash 低地址，应用升级不能擦除 Bootloader。
2. 新镜像写入非活动槽，不能覆盖当前已确认镜像。
3. 只有整镜像 CRC32 正确后，镜像才可进入 `PENDING`。
4. 新应用必须在启动和自检完成后调用 `BOOT_Confirm()`。
5. 新应用未确认、看门狗复位或启动异常时，Bootloader 自动回到旧确认镜像。
6. CAN 中断、断电、数据包丢失、重复包或乱序包不能破坏旧确认镜像。
7. PC 工具一次只操作一块板；板端只有完整 UID 匹配且当前无其它会话时才接受升级。现场单一升级主站是已确认的操作规则，不为第二台 PC 同时接入设计跨板仲裁。
8. 每块板升级后由 PC 工具确认新版本与健康状态，再继续下一块。升级全程不能要求 L431 分配 NodeID；亮紫灯的未分配状态也必须可以进入升级并完成确认。
9. Bootloader 失效属于必须通过 SWD 处理的初始安装或极端故障，不以 CAN 升级替代首次 SWD。

## 3. 芯片和现有工程约束

STM32L432KBU6：本项目实物为 STM32L432KB，128 KB 单 Bank Flash，64 页，每页 2 KB；Flash 只能按 64 bit 双字编程。当前应用 ELF 的 text/data 总量约 46 KB，当前 CAN 为标准 11 位 ID、500 kbps。

现有装甲板通过 STM32 UID 枚举，NodeID 只在 RAM 中有效。24 位 FNV token 和 UID CRC16 可用于快速筛选，但存在碰撞可能；升级建链必须核对完整 12 字节 UID，不能只使用 NodeID 或截断 token。

现有入口：

- 装甲板应用：`new_armor/Armor_Cmzy26_081`
- 装甲板 CAN 业务：`App/comm/board_comm.c`、`App/comm/can_node.c`
- CAN 协议文档：`new_armor/Armor_Cmzy26_081/Docs/CAN_PROTOCOL.md`

## 4. Flash 分区

| 区域 | 起始地址 | 结束地址 | 大小 | 说明 |
|---|---:|---:|---:|---|
| Bootloader | `0x08000000` | `0x08007FFF` | 32 KB | 16 页；量产阶段启用 WRP |
| App Slot A | `0x08004000` | `0x0800FFFF` | 48 KB | 24 页 |
| App Slot B | `0x08010000` | `0x0801BFFF` | 48 KB | 24 页 |
| Metadata | `0x0801C000` | `0x0801FFFF` | 16 KB | 8 页；保存双备份记录 |

Bootloader、Slot A、Slot B 必须分别使用独立 linker。应用向量表不再位于 `0x08000000`，跳转前必须设置 `SCB->VTOR`、MSP 和 Reset_Handler。当前 `system_stm32l4xx.c` 的 VTOR 偏移为 0，必须验证应用的 `SystemInit()` 不会把 Bootloader 设置的 VTOR 改回低地址。

A/B 两槽地址不同，同一绝对地址链接的 `.bin` 不能直接写入另一槽执行。构建系统必须产出 Slot A 和 Slot B 两个镜像，PC 工具依据目标空槽选择对应镜像，并校验镜像声明的槽位与地址。

### 4.1 Metadata 内容

每条记录至少包括：magic、格式版本、记录序号、UID 校验、活动槽、Slot A/B 状态、镜像大小、镜像版本、镜像 CRC32、启动尝试次数、记录 CRC32。

Metadata 至少使用不同 Flash 页上的两份带序号记录。先写并回读新记录，验证 CRC 后才允许擦旧记录；掉电时选择 CRC 正确且序号最新的记录。必须说明循环写入和磨损策略，不能仅靠两份记录声称掉电安全。

状态建议：`EMPTY`、`DOWNLOADING`、`VALID`、`PENDING`、`CONFIRMED`、`BAD`。

## 5. CAN 升级协议初版

协议使用标准 11 位 CAN ID，所有升级命令、数据与响应均放在装甲板调试层 `0x100~0x10F`。下表是 ID 草案；发布前须同步更新当前生效的 `Docs/CAN_PROTOCOL.md`。当前应用虽在硬件滤波层接收整个 `0x100~0x17F`，应用分发并不处理 `0x100~0x10F`，且未取得 NodeID 时会跳过业务帧；升级入口必须独立于 NodeID，能在枚举尚未完成时按完整 UID 建链。

| ID | 方向 | 名称 | 作用 |
|---:|---|---|---|
| `0x100` | PC→板 | `FW_CMD` | 发现、进入 Bootloader、开始、完成、回退、重启 |
| `0x101` | PC→板 | `FW_DATA` | 带 session 和 packet sequence 的固件数据 |
| `0x102` | 板→PC | `FW_ACK` | 命令、块提交、错误和重试响应 |
| `0x103` | 板→PC | `FW_STATUS` | Bootloader 状态、版本、进度和启动结果 |

ID 复核：现行枚举用 `0x120~0x123`，业务帧为四个 NodeID 的 `0x130~0x16C`，枪管用 `0x2xx`；当前代码没有发送或处理 `0x100~0x10F` 的路径。升级时没有 L431，装甲板不会收到业务枚举与轮询帧。

### 5.1 定址

控制握手须分帧传输完整 12 字节 UID，并绑定 session；token 与 CRC16 只作快速筛选。数据帧只被接受该 session 的目标板处理。非目标板不回复数据帧；已占用的板应拒绝新的会话。发现阶段 2–4 块板可能共用响应 ID，须设计 UID 派生应答时隙及冲突重试，不能同时回复 `0x103`。PC 工具串行调度；不引入 L431 授权或多 PC 全局锁。

### 5.2 传输

- 每个数据帧携带 16 位 packet sequence 和 5 字节固件数据。
- 每 32 帧组成一个 block。
- Bootloader 收齐并写入 Flash 后回复 block ACK；页擦除/编程期间主站必须等待明确的 READY，不得连续灌包。该芯片是单 Bank，Flash 操作会阻塞同 Bank 取指和 CAN 响应。
- 主站超时只重发当前 block。
- 重复包必须幂等；错误序号必须返回明确错误码。
- 最后执行整镜像 CRC32，成功后写 `PENDING` 并复位。5 字节载荷需要在板端拼成 8 字节对齐双字，镜像末尾补齐字节不计入镜像 CRC。

CRC32 统一采用实现时冻结的参数，PC 工具和 Bootloader 必须共享同一测试向量。CRC 只防止传输或存储错误，不提供固件来源认证；维护模式的访问控制和误触发防护仍须设计。

### 5.3 升级接线与现场条件

升级时允许 L431 保持在 CAN 链路上。PC 工具不得把 NodeID 或四块板必须同时存在作为升级前提；目标装甲板完成 UID 选择后暂停比赛 CAN 业务，再由 ENTER 复位进入 Bootloader。现场需保证 CAN_H/CAN_L、公共地、供电、500 kbps 波特率和总线两端正确终端；连接 USB-CAN 时避免额外终端电阻。

没有 L431 时，当前应用会保持 NodeID 未分配并可能亮紫灯。升级入口必须在 `CanNode_IsReady()` 判断之前处理调试层命令；Bootloader 的发现、传输和新应用确认都不依赖业务枚举。

## 6. 升级状态机

### 6.1 应用侧

`NORMAL → MAINTENANCE_REQUEST → 写入 Boot 请求标志 → 系统复位`。

进入维护模式前：停止 ADS131M04 采样、停止击打事件发送、清理普通 CAN 发送队列，避免升级期间占用总线。进入命令只能由升级协议完整目标握手触发，普通广播发现不能使四板同时复位。

### 6.2 Bootloader 侧

`STARTUP → CHECK_METADATA → WAIT_COMMAND → ERASE_TARGET → RECEIVE → VERIFY → PENDING → BOOT_TRIAL → CONFIRMED/ROLLBACK`。

Bootloader 必须独立初始化时钟、CAN 和看门狗，不能依赖应用的 HAL 状态。试运行的复位与回退规则须定义：通过持久化的试运行计数及启动确认管理，复位后优先回退旧槽；若启用独立看门狗，应用也必须按约定喂狗，否则好镜像会反复复位。

### 6.3 PC 工具侧

1. 读取当前连接的 1–4 块板 UID、当前槽位、版本和状态。
2. L431 在线时由上位机先确认静默；无 L431 时直接升级；始终只有一台 PC 的 USB-CAN，板端 session 锁保护当前目标板。
3. 选择一个 UID 目标。
4. 发送进入 Bootloader 命令并等待状态确认。
5. 发送镜像、处理 block ACK 和重试。
6. 等待 Bootloader 校验、试启动和应用确认。
7. 在无 NodeID 的条件下确认目标板应用版本与自检状态，释放该板会话，再处理下一块。
8. 本次选定的全部板完成后复查 UID、版本和状态；接回业务总线后的 L431 联调只作为额外兼容性检查。

## 7. 实施任务

### Phase 0：规格冻结

- 冻结 CAN 帧字段、错误码、CRC32 参数和版本格式。
- 冻结 Metadata 结构和两个 linker 地址。
- 生成协议测试向量。
- 冻结完整 UID 分帧握手、2–4 板发现退避、单升级主站操作流程和异常退出恢复规则。

### Phase 1：Bootloader 基础

- 建立独立 Bootloader 工程。
- 实现 CAN 接收、Flash 页擦除、64 位写入、CRC32。
- 实现 Slot A 检查和应用跳转。
- 实现看门狗、向量表切换和异常复位诊断。

### Phase 2：A/B 应用框架

- 将当前应用链接到 Slot A。
- 增加 Slot B 构建配置。
- 实现 `BOOT_RequestUpdate()` 和 `BOOT_Confirm()`。
- 应用启动和本地自检完成后确认版本，不等待 L431 或 NodeID。
- 升级维护模式停止 ADS、HitDetect 和业务 CAN。
- 验证两个地址分别链接的应用在复位后均正确设置 VTOR，并定义应用喂狗与确认时机。

### Phase 3：CAN 传输

- 实现命令、session、packet sequence、block ACK。
- 实现断包、重复包、超时、取消和错误状态。
- 实现 Metadata 双记录和断电恢复。

### Phase 4：PC USB-CAN 工具

- 设备发现和 UID 列表。
- 单目标升级和进度显示。
- CRC32 校验、超时重试、日志保存。
- 四板串行升级编排。
- 检测已有单板升级会话；按目标槽选择对应镜像；支持只接 1 块板和最多 4 块板。

### Phase 5：可靠性验证

- 断 CAN、断电、复位、错误镜像、错误 UID、错误 CRC。
- 新应用不确认、HardFault、看门狗复位。
- 1、2、3、4 块板分别连接时完成发现和升级；多板时只有目标板进入 Bootloader。
- 连续升级和无 NodeID 的新应用确认测试。
- 实测发现帧碰撞、Flash 擦写期间收发和双槽地址选择；不测试 L431 共线升级。

### Phase 6：量产保护

- Bootloader 完成 HIL 测试后启用 Bootloader 页 WRP。
- 暂不启用 RDP2。
- 保留 SWD 救援流程和 Bootloader 版本查询。

## 8. 风险复核与验证门槛

| 优先级 | 风险 | 当前证据 | 必须完成的控制与验证 |
|---|---|---|---|
| 高 | 未分配 NodeID 时无法进入升级或无法确认新应用 | 当前接收分发在 `CanNode_IsReady()` 为假时跳过业务帧，紫灯表示通信丢失 | 调试层升级命令在该判断前处理；1 块板、无 L431、紫灯状态完成升级和新应用确认 |
| 高 | A/B 镜像地址不匹配，试启动后立即异常 | 当前工程只链接到 `0x08000000`，`SystemInit()` 设置 VTOR | A/B 双构建；镜像头检查目标槽位；分别从两槽冷启动及中断验证 |
| 高 | 元数据写入途中掉电使两个槽状态都不可判定 | 单 Bank Flash，每页 2 KB、双字编程 | 不同页双记录、写后校验、最后提交；每个擦写阶段故障注入 |
| 高 | 新固件未确认时持续复位，无法回退 | 当前装甲板应用没有 IWDG，确认接口尚未实现 | 定义试运行次数/时间、喂狗契约和复位原因；故意 HardFault/卡死/不确认验证旧槽启动 |
| 高 | 2–4 块板发现响应碰撞或选错板 | 多块板共用升级响应 ID；NodeID 不存在 | 发现阶段 UID 派生时隙与重试；完整 UID 建链；实测仅目标板进入升级 |
| 中 | 单 Bank Flash 擦写时丢失 CAN 帧或超时 | Flash 操作会暂停同 Bank 取指 | 停等式页事务，擦写前发 BUSY、结束后发 READY；测量最坏擦写时间和 CAN FIFO 溢出 |
| 中 | 24 位 token + CRC16 错选目标 | token/CRC 均为截断校验 | 建链核对完整 12 字节 UID；主机与板端都拒绝不匹配 UID |
| 中 | 维护命令误触发或恶意升级 | CRC32 不验证发布者身份 | 命令须匹配完整 UID 与当前 session；维护模式限时；量产环境若需要抗篡改再增加签名 |
| 中 | Flash 布局被参数保存功能侵占 | `Cal_Save` 仍是桩，未来可能占用尾页 | 统一内存布局常量；构建时断言区域边界；参数持久化仅使用明确保留页 |
| 中 | Bootloader 首次烧录或 WRP 配置错误 | 首次安装仍依赖 SWD | 单板先验证、保留 SWD 救援；四板验证通过前不启用 WRP，不启用 RDP2 |

纯代码审查目前只能确认 ID 分配没有直接重叠，无法证明四板总线时序、断电原子性或真实回退行为。上述高优先级项未通过实板测试前，不得称为可靠升级。

## 10. L431 共线静默方案（当前执行边界）

升级时由上位机统一控制 L431：

1. 上位机发送 L431 进入升级静默态的维护命令；
2. L431 停止枚举、比赛业务和周期性 CAN 发送，并回复静默确认；
3. 上位机确认静默后，再执行装甲板 UID 发现和 A/B 升级；
4. 所有目标板升级完成并确认后，上位机发送 L431 恢复命令；
5. L431 恢复正常 CAN 业务。

当前第一版协议使用调试层 ID `0x110`/`0x111`：请求帧为 `A5, session, command, 0,0,0,0,0`，其中 command=`1` 进入静默、`0` 恢复；应答帧为 `5A, session, command, status, 0,0,0,0`。静默命令必须具备 session、超时和明确应答；L431 未确认静默时，上位机不得开始装甲板数据传输。后续工作集中在 L431 固件、上位机协调流程和联调测试，不再继续通过调整装甲板窗口规避 L431 总线流量。

只有同时满足以下条件才算完成：

- 当前连接的 1–4 块板均可通过 UID 正确选择，缺板不阻塞升级。
- 单板升级中断后旧版本可运行。
- 新版本启动失败自动回退。
- 升级结束后目标板在无 NodeID 条件下报告新版本与本地健康状态；恢复业务接线后的枚举另行检查。
- 其它连接的装甲板不进入 Bootloader、不接收目标板镜像。
- PC 工具能给出明确的成功、回退、超时和不可恢复错误。
- 完成至少 50 次连续升级和随机断电测试。
