# CAN Bootloader 使用说明

这份说明面向接手审查和实机操作的开发者。当前仓库由 LukasXu 完成初版实现；建议先按本文完成静态检查，再进行一次单板烧录。

## 目录说明

- `Boot/`：独立 Bootloader 工程。
- `App/comm/fw_*.c,h`：装甲板应用侧升级入口、维护态和布局定义。
- `build_A/`、`build_B/`：A/B 槽应用镜像输出目录（构建产物，不提交）。
- `tools/armor_fw_update.py`：自动发现、A/B 选择、L431 静默协调和升级工具。
- `tools/armor_can_tool.py`：ControlCAN/USBCAN2 封装及调试工具。
- `tools/make_initial_image.py`：拼接首次 SWD 镜像。
- `docs_canboot/`：协议、风险、进度和本说明。

## 构建

在仓库根目录执行：

```powershell
make -j2 SLOT=A all
make -j2 SLOT=B all
make -j2 -C Boot
python tools\make_initial_image.py --boot Boot\build\armor_boot.bin --slot-a build_A\Armor_Cmzy26_081_A.bin --output build\initial_image.bin
```

或使用 VS Code 任务 `STM32: Build All Firmware`、`STM32: Generate Initial Image`。

## 首次 SWD 烧录

首次安装或 Bootloader 变更后使用 VS Code 任务：

```text
STM32: Flash Initial Image (J-Link)
```

它烧录 `build\initial_image.bin`，包含 Bootloader 和 Slot A。烧录前确认芯片为 STM32L432KB、目标板供电正常。后续普通升级不需要 J-Link。

## CAN 升级

使用 64 位 Python 3.10、ControlCAN.dll 和 USB-CAN 通道 1：

```powershell
python tools\armor_fw_update.py --list --channel 1
python tools\armor_fw_update.py --channel 1
```

工具会先固定开局发现到的 UID 集合，之后每块板开始前重新确认在线状态。掉线目标会警告并暂缓；后续重新上线会继续加入队列。所有当前在线目标完成后等待约 3 秒，仍未恢复的目标不再阻塞本次任务，并在末尾报告 `initial/updated/missing`。开局后新出现的 UID 不加入本次任务。L431 在线时，工具先请求 `0x110` 静默并等待 `0x111` 确认；没有 L431 时会提示并直接升级装甲板。升级完成或异常退出时，已确认静默的 L431 会恢复。全部传输结束后工具发送一次现有 `0x120` 枚举启动帧，收齐目标 UID 的 `0x121` 四个分片后才打印 `application=verified`，用于确认确实进入应用程序。

升级前检查 500 kbps、CANH/CANL、公共地和终端电阻。工具发现目标后会先让所有已发现装甲板进入 Bootloader，减少非目标板业务帧对 32 包窗口的干扰；第一次测试仍建议只连接一块装甲板，确认成功后再扩展到 4 块。

## 审查重点

1. 检查 `Boot/main.c` 的 Flash 边界、A/B 槽地址、CRC 和试运行回退。
2. 检查 `App/comm/fw_entry.c` 的 UID 选择和维护态是否会误停比赛业务。
3. 检查 L431 静默协议 `0x110/0x111` 与 `L431PM/Application/Referee/app_referee_can.c` 的应答一致性。
4. 先做单板 A/B 循环、断 CAN、断电，再做 4 板顺序升级。

遇到升级失败时保留完整终端输出和 UID；不要立即覆盖初始镜像，先记录失败阶段和 `window retry` 信息。
